让大模型
真正替用户办事

基于大语言模型的宠物寄养与健康管理智能体

我想做的不是一个宠物店管理系统，而是一个能真正替用户办事的领域智能体。PawCare 把宠物档案、疫苗提醒、笼舍空档和寄养订单做成可靠的业务底座，再让大模型通过 8 个受权限约束的工具去查数据、算空档、起草预约。

关键在边界：Agent 只能生成草稿，确认订单必须由用户在前端点一下，确认接口不对模型开放。这样它既有行动能力，又不会越权或擅自下单。目前已经跑通真实模型、RAG、SSE 和 91 条评测，并用 6 个变体做了消融，能拿出可复现的实验结果。

01

选题背景

宠物寄养的需求在增长，但信息仍然散落在聊天记录、纸质登记和多个系统里。

宠物主想寄养，往往要先翻疫苗本、再问有没有笼位、再反复确认时间；寄养员接手时，也不一定看得到完整的健康记录。传统后台把每一步都做成菜单，用户得自己找入口；通用聊天机器人能回答，却碰不到真实数据，也不能安全地写业务表。

档案断点

健康信息不连续

疫苗、驱虫、用药、忌口分散在不同地方，寄养交接靠口头说明。

操作断点

跨表任务要跳很多页

查健康记录、查提醒、查空笼、填预约，本来是一句话的事，被拆成四五个页面。

智能断点

会聊天，但不会办事

通用助手没有业务数据和权限，也无法安全地完成预约这类写操作。

题目的落点：不是再做一个 CRUD 后台，而是研究一个更具体的问题：当大模型进入真实业务写操作时，怎样让它有能力办事，同时又把不可逆动作关在安全边界之外。

02

用户与任务

同一个 Agent，面向三种角色，能力和可见范围不同。

角色 一句话任务 对应能力
宠物主 “豆豆下个月寄养 5 天，疫苗快到期吗？有没有合适笼舍？” 查健康记录、查提醒、算空档、生成预约草稿
寄养员 “今天哪些订单入住？年糕的日报写了吗？” 查订单、查每日报告、查看入住安排
管理员 “这周订单和用户情况如何？” 全局查询、审计与数据维护

用户身份由 JWT 解析，工具参数里没有 user_id。模型不能通过编一个参数来冒充别人，权限判断在服务层完成。

03

系统构思

一个底座，一条主线，四道边界。

一个底座

先把业务做对

宠物档案、健康记录、提醒、笼舍、寄养订单、每日报告。Agent 的每个工具都落在真实业务表上，不是 mock 数据。

一条主线

显式工具循环

问题 → 模型 → 工具调用 → 服务层 → 结果 → 模型 → 回答。每一步都能记录和检查，不把框架当黑盒。

四道边界

能力与约束一起设计

权限、确认、知识、评测。让 Agent 能行动，但行动范围是可解释、可验证的。

权限边界

身份来自 JWT，服务层做行级过滤。工具不接受模型传入的用户身份。

确认边界

草稿 15 分钟有效；确认是独立 REST 接口，不在 Agent 工具表里。

知识边界

RAG 只回答知识库覆盖的内容；没有依据就拒答；回答标注来源。

评测边界

91 条用例、6 个变体；每次改动都有对照实验，不靠单个 demo 判断成败。

04

关键设计

4.1 八个工具，写操作只有一个

工具是 Agent 和业务系统之间的唯一通道。读工具负责查，草稿工具负责起草，知识工具负责检索。注册表里没有确认工具，也没有改订单状态、办理入住或退房的工具。

list_my_pets 读

列出当前登录用户的宠物。

get_pet_health_records 读

查疫苗、驱虫、病历等健康记录。

get_upcoming_reminders 读

查临期的疫苗、驱虫和用药提醒。

check_kennel_availability 读

按日期和笼型查可用笼舍。

create_boarding_draft 草稿

生成寄养预约草稿，不创建订单。

list_boarding_orders 读

查当前用户可见的寄养订单。

get_boarding_daily_reports 读

查寄养期间的每日报告。

search_care_knowledge RAG

检索护理知识库，返回片段与来源。

写操作只有一个：create_boarding_draft，而且它只写草稿。模型没有 confirm_boarding_draft，没有改订单状态的工具，也没有入住、退房工具。

4.2 草稿确认：把不可逆操作交给用户

Agent 生成草稿后，前端展示宠物、日期、笼舍、金额和 15 分钟倒计时。用户点击确认，才调用独立的 REST 接口。接口会再次校验 JWT、草稿所有权、幂等键和笼舍占用。

4.3 权限：身份不经过模型

JWT 解析出用户 ID 和角色，工具 handler 只接收当前用户上下文。服务层按 owner_id 和角色做行级过滤。评测里专门有跨用户用例：owner 查不到 owner2 的可乐，owner2 也查不到豆豆的疫苗记录。

4.4 RAG：知识回答要有依据

知识库当前有 14 篇护理知识，使用 BAAI/bge-small-zh-v1.5（512 维）做向量检索，并与词法检索混合排序。回答要求标注“（来源：标题）”；没有足够依据时拒答。知识库片段、宠物备注和日报都按不可信上下文处理，防止提示注入。

生产路径保留 PostgreSQL + pgvector 与 HNSW 索引；本地开发用 SQLite 跑通链路，评测时复制隔离数据库，避免污染演示数据。

06

评测与证据

评测不是只跑几条 demo，而是把开发库复制成隔离评测库，用真实模型走完整 HTTP 链路。

91 评测用例
6 消融变体
8 权限感知工具
64 后端测试

用例覆盖宠物、健康、提醒、预约草稿、订单、日报、空档、知识、权限、注入、拒答、多工具和澄清 13 类场景。运行器自动统计任务成功率、工具选择准确率、参数准确率、平均延迟、P95 延迟和 token 消耗，输出 JSON 与 CSV 报告。

首轮完整评测 91 条通过 87 条（95.6%），工具选择准确率 97.8%，参数准确率 100%，平均延迟 8.5 秒，P95 17.4 秒，总 token 约 42 万。4 条失败中 2 条是网络回退，2 条是断言过严；修正后重跑 4/4 通过。

消融实验：把设计逐个拿掉

变体 通过 它验证了什么
full 12/12 完整系统，作为对照基线。
no_tools 0/12 没有工具，模型无法完成任务，说明工具是行动能力的前提。
no_rag 8/12 去掉检索后，3 条知识问答和 1 条引用用例失败。
no_permission 9/12 去掉行级权限后，出现 3 条跨用户数据泄漏。
no_citation 11/12 去掉引用约束后，回答不再稳定标注来源。
no_draft_confirmation 11/12 去掉确认边界后，模型会自行调用确认工具并真的创建订单。

结论：每个设计都不是装饰。没有工具，任务完成率是 0；没有权限，会出现跨用户泄漏；没有确认边界，模型会真的下单。这些结果可以直接写进论文的实验章节。

09

可能被问到

会上大概率会问这几件事，先把答案准备好。

这和普通管理系统有什么区别？

普通系统要求用户自己找菜单、自己填表；这里用户用一句话描述任务，Agent 负责跨表查询、计算空档并起草预约。区别不在界面，而在任务完成方式。

为什么不用 LangChain 或 LangGraph？

显式循环更适合这个项目的目标：每一步消息、工具调用和 trace 都能单独检查，方便做权限和评测。框架不是目的，后续需要时也可以替换。

模型胡说怎么办？

业务事实以工具结果为准，知识问答走 RAG 并要求引用来源；没有依据就拒答。写操作不靠模型自律，而靠确认边界和接口校验。

Agent 会不会自己下单？

不会。确认工具不在注册表里，模型只能生成草稿；订单必须由已登录用户点击确认，接口还会再次校验所有权、幂等键和笼舍占用。

权限怎么保证？

身份由 JWT 注入，不接受模型传入的 user_id；服务层做行级过滤。评测里有跨用户用例，去掉权限后会出现可复现的数据泄漏。

工作量够不够？

不是只有一个对话页面：业务底座、8 个工具、RAG、SSE、前端、数据库迁移、64 条测试和 91 条评测都在仓库里，消融实验也能复现。

为什么选 DeepSeek？

它提供 OpenAI 兼容接口，工具调用可用，成本可控。模型在代码里是可替换的，评测跑的是真实 API，不依赖某一个模型的演示效果。

下一步做什么？

先把前端视觉和部署打磨好，再补通知中心和论文材料；主链路和评测不再大改，避免为了展示效果牺牲可验证性。
